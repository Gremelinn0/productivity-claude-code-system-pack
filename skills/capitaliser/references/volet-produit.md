# Faits produit, décisions et état d'exécution

Distinguer quatre objets et utiliser leurs sources existantes :

| Objet | Source habituelle |
| --- | --- |
| Ce que le produit ou le process doit faire | contrat produit ou procédure métier |
| Pourquoi cette décision a été retenue | décision datée chez le propriétaire |
| Ce qui reste à exécuter | plan ou file d'exécution |
| Ce qui a effectivement été observé | résultat/test daté et journal de preuve |

Une ligne d'avancement n'entre pas dans un contrat stable. Une décision ne devient pas
une spécification générale parce qu'elle a été utile sur un cas particulier.

Écrit, livré et observé sont distincts. Décrire un comportement avant de l'avoir exercé
reste une intention. Les tests ne prouvent que leurs scénarios ; un accusé d'outil ne
prouve pas l'effet côté utilisateur. Une promesse d'absence demande une population, une
fenêtre et un témoin qui aurait permis de voir le défaut.

Lorsqu'un changement rend fausses une fiche QA ou une description fonctionnelle, les
réconcilier dans la même passe autorisée. Un indicateur de couverture ne doit pas compter
une procédure de secours comme preuve du fonctionnement nominal.

Ne pas modifier une règle de facturation, un workflow actif ou une décision produit pour
faire correspondre le système à une note de capitalisation. Garder la divergence mesurée
et la faire trancher au bon niveau.
